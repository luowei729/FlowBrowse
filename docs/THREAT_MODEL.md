# THREAT_MODEL.md — FlowBrowse 威胁模型与合规边界

## 1. 诚实的能力边界（对外不承诺、对内不误导）

- **有效 TLS 证书 + 自有域名 + UDP 443** 只保证能建立"看起来正常"的 HTTPS/HTTP3 连接，**不保证穿越 GFW**。
- Chrome 原生支持 QUIC ≠ 扩展能创建任意 QUIC 隧道或接管全部流量（详见 ARCHITECTURE 第 5 节）。
- 本项目的**全量接管**依赖 TCP `https` 代理，**QUIC 仅用于应用层探测/信令/加速**，二者定位不同，勿混淆宣传。

## 2. GFW 对抗面（已知风险，非保证项）

| 风险 | 说明 | 缓解 |
|---|---|---|
| SNI 检测 | 明文 SNI=`sel2.lkz.pub` 可被识别与阻断 | 用普通可信域名；必要时 ECH（浏览器侧，非本项目可控） |
| UDP 443 QoS/干扰 | GFW 可对可疑 IP 的 UDP 443 限速/丢包 | WebTransport 失败自动回退 TCP 主干；h3 探测仅参考 |
| 代理协议特征 | CONNECT/绝对形式请求有指纹 | Caddy 与站点同端口混流，普通访问返回默认页降低可疑度 |
| IP 关联 | 服务器 IP 被标记后连带封域名 | 域名与 IP 解耦、可随时换 IP/加节点 |

## 2.5 转发代理隐蔽性（主干通道防嗅探）

针对"CONNECT/绝对形式请求会不会被嗅探"，区分两类对手分别处理：

- **链路中间人（GFW/DPI）嗅探内容**：主干用 Chrome 原生 `https` 代理 scheme。Chrome 先与服务器做一次到自有域名 SNI 的标准 TLS 握手，之后所有 CONNECT 与绝对形式请求都在这条 TLS 内密文传输。GFW 仅看到"用户在访问 `DOMAIN` 这个 HTTPS 站点"，**读不到被代理的目标域名/内容**。→ 内容级嗅探由 TLS 解决。
- **主动探测 443 判定是否代理**：
  - 强制 BasicAuth：无凭据 CONNECT 返回 407，端口**从不以开放代理行为响应**，扫描器无法取证。
  - 转发不注入 `Via`/`X-Forwarded-For`，不泄露后端身份。
  - 根路径返回空 200（逐字节等同未配置的 Caddy 默认）：非代理请求看起来就是一个普通站点，无代理特征。
  - **不记访问日志**：服务端不记录 CONNECT 目标，避免二次泄露用户访问记录。

**残余风险（不可由协议加密消除）**：被代理目标域名对**服务器本身**可见（非 GFW）；GFW 仍可能通过 IP 情报、连接时长与流量相关性分析产生怀疑，属"IP 是否被封"层面，需靠换 IP/域名、多节点缓解。

## 3. 访问控制

- 转发代理需 `Proxy-Authorization` BasicAuth，避免成为开放代理被滥用。
- 订阅接口需 `token`；token/凭据内嵌于 `fb://` 链接，属自托管敏感信息，**导出/分享需自行注意**。
- 证书与私钥仅在服务器 `/etc/flowbrowse/`，不入仓库、不入记忆。

## 4. 合规与用途

- 定位为开发者/研究者自托管的网络调试与合规访问工具。
- 分发默认自用/小范围，**不上架 Chrome Web Store**（商店对代理/VPN 类有政策限制）。
- 使用者须遵守所在地区法律法规；本项目不对用途负责。

## 5. 数据与隐私

- 扩展本地配置存 `chrome.storage`；不落第三方。
- 主干代理由使用者自有服务器承载，日志策略由使用者在服务端自行控制（默认 Caddy 不记录请求体）。
